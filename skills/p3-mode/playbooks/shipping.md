### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

1. **Verify each PR independently before it lands.** Use GitHub CLI (`gh`). Link every PR with `link_pull_request` and read the stack with `list_thread_pull_requests`. Send one `delegate_task` per PR, with a self-contained read-only brief, `mode: "async"`, and a named verifier role resolved through `orchestrator_capabilities`. Drain with `task_status`. Each verifier runs parent against head on the real surface, using `preview_*`, `device_*`, or the project's CLI driver. The parent posts its `PASS`, `PASS+NOTES`, or `FAIL` verdict on the PR. A verifier must not be the author. Green CI and bot approval are not live verification.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.
4. **Land bottom-up, one PR at a time.** Confirm that the lowest unmerged PR targets trunk before running `gh pr merge <pr> --squash`. A PR targeting its parent's branch merges into that branch, not trunk. Read back `gh pr view <pr> --json state,mergedAt,baseRefName`. A requested or queued merge is not a completed merge. Arm `--auto` only when the user authorized merge-when-ready and the verdict covers the current head. Once that PR is merged into trunk, retarget its immediate child with `gh pr edit <pr> --base <trunk>`, move its patch onto the merge result, and push with `--force-with-lease` pinned to the known remote head. Apply step 3 and wait for fresh checks before merging it.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only branch or base change. Arm `watch_pull_request` on the lowest unmerged PR and end the turn. On wake, read its state and confirm it merged into trunk before moving to its child. A base moving to trunk when its parent merges is expected. Diagnose a stalled merge before mutating anything. Call `unwatch_pull_request` when handing control back to the operator.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what landed and how you confirmed it, and what the next gap needs.
